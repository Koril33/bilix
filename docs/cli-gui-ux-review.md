# BiliX CLI 与 GUI 人机交互与产品体验评审

评审对象：BiliX 1.6.0 当前代码与使用文档  
评审日期：2026-10-04  
评审视角：产品设计、命令行交互、桌面应用任务流程

## 1. 结论摘要

BiliX 的下载内核已经具备扎实的安全与可靠性基础：CLI 和 GUI 共用解析、权限判断、下载规划、流传输、媒体校验和原子提交；下载失败不会直接覆盖旧文件；CLI 已支持批量、多 P、画质/编码/音轨选择、拼写提示和多种 Shell 补全。

主要差距在产品交互层。GUI 目前以单页表单和当前窗口内的临时任务表为中心；CLI 具备较多命令和参数，但配置修改、下载过程的机器输出与更清楚的使用引导不足。成熟下载工具通常把任务生命周期作为主要交互对象：用户能看到排队、下载、校验、完成与失败，并对任务执行暂停、重试、移除、恢复或打开文件等操作。BiliX 当前更接近“可靠的下载操作入口”，还没有完整成为“可管理下载任务的工具”。

建议按以下次序推进：

1. 先修复信息呈现、任务列表被覆盖、重试语义不清、设置来源不清等现有体验问题。
2. 再补充可追加、可逐项控制的任务队列、清晰的进度反馈和失败恢复流程。
3. 最后设计任务持久化、暂停/续传、并发与速度控制。暂停和续传要由内核与界面共同支持，不能只加 UI 按钮。

## 2. 评审范围与限制

本评审检查了 README、CLI/GUI 使用说明、架构和路线图，审阅了 CLI、GUI 窗口、后台 worker、下载服务、配置和终端展示代码，并查看了 CLI 的实际帮助输出。功能范围包括：

- CLI：帮助/版本、info 与 JSON、download 与批量列表、多 P/选集、画质/编码/音轨、严格匹配、覆盖、dry-run、quiet、扫码登录/账号状态/退出登录、配置查看、doctor、Tab 补全和拼写建议。
- GUI：下载输入、URL 文件导入、信息查看、下载选项、预览计划、任务表、进度、取消、失败/取消重试、扫码登录、账号状态、设置和诊断。
- 共用行为：URL 解析、账号授权判断、选集发现、下载计划、文件冲突、音视频传输、媒体校验、合并、临时目录和最终提交。

当前工作环境没有安装 PySide6，本轮没有启动真实 GUI 进行视觉、键盘或桌面会话验收，也没有使用真实账号下载。相关判断以源码和文档为依据。外部资料用于提供成熟交互模式的参考，不代表必须逐项照搬特定平台的设计。

## 3. 现有功能与值得保留的基础

### 3.1 CLI 功能

| 命令或入口 | 当前能力 | 产品评价 |
| --- | --- | --- |
| 根命令 | 帮助、版本、旧入口兼容 | 入门路径尚可，帮助文字中有中英文混排 |
| info | 单条或批量查询；人类可读表格或 JSON | CLI 的清晰度、音轨和选集信息比 GUI 呈现完整 |
| download | 多 URL、URL 文件、多 P、画质/编码/音轨、strict、dry-run、覆盖、quiet、FFmpeg 路径 | 功能覆盖全面；一次命令参数较多，初学者需要自行理解术语 |
| auth | 扫码登录、状态、JSON 状态、退出登录 | 本地凭据与共享配置设计明确；终端登录需处理二维码图片 |
| config / doctor | 查看配置；检查版本、配置位置和 FFmpeg | doctor 能力清楚；仅 CLI 用户不能通过命令方便地修改配置 |
| completion | Bash、Zsh、Fish、PowerShell 补全；拼写纠正 | 是现有 CLI 的优势，应继续保留和维护 |

### 3.3 建议保留的产品优势

- CLI 和 GUI 共享业务内核，权限、降级、事务和校验逻辑不容易因前端而分叉。
- 默认行为较安全：同名文件跳过；覆盖在新媒体通过校验后才提交；普通失败保留临时材料供排查。
- GUI 将网络、下载和 FFmpeg 工作放在后台线程，避免把耗时操作放在 Qt 主线程。
- CLI 的参数补全、路径候选和相近指令提示显著改善了命令可发现性。
- 严格匹配与默认降级并存，兼顾“尽量下载成功”和“必须精确满足画质”的不同需求。

这些能力是体验改进的底座。后续宜扩展共同的任务状态、错误分类和进度事件，而不是在 GUI 另写下载逻辑。

## 4. 主要体验问题与建议

以下优先级按用户影响和产品收益排序，不等同于工程难度。路线图已经涵盖其中多项，建议将本文作为产品背景，与[下一版本建议](roadmap.md)合并排期。

### P0：优先修正现有交互中的可见问题

#### 4.1 GUI 信息查询应使用可读的信息视图

GUI 的查看信息操作会把 public_dict 序列化成 JSON，再写入只读文本框；CLI 的 info 则用清晰度、音轨、选集表格呈现。这让 GUI 用户面对的是面向程序的数据结构，而非帮助其选择下载内容的界面。

建议将信息拆成标题/UP 主/时长、账号可获取的画质与编码、可用音轨、选集几个区块；清晰度不可用、需要账号权限、试看或 DRM 等状态应解释原因和后续操作。多 P 内容直接提供可勾选的选集清单，并展示选中数量和预计任务数。当前选集输入是一个应用于所有地址的文本字段，无法在同一批次中为不同视频选择不同选集；可视化选择应按视频分别设置。若保留 JSON，应作为“复制 JSON”或“查看原始数据”的辅助功能。

可参考 GNOME 对列表/列视图的建议：列表项应易读、信息层次明确，并适配动态内容；集合操作应与具体项目对应。[GNOME 列表与列视图指南](https://developer.gnome.org/hig/patterns/containers/list-column-views.html) [GNOME 集合选择模式](https://developer.gnome.org/hig/patterns/containers/selection-mode.html)

代码依据：[GUI worker 的信息序列化](../src/djhx_bilix/gui/worker.py#L215)、[GUI 信息框更新](../src/djhx_bilix/gui/app.py#L579)、[CLI 人类可读信息展示](../src/djhx_bilix/presentation.py#L24)。

#### 4.2 新批次不应静默抹掉旧任务结果

开始下载或预览计划时，当前 GUI 会清空任务表并重建行。用户若没留意，上一批的成功、失败和输出位置就从窗口中消失；任务记录也不会在退出后保存。

建议区分“加入队列”和“开始处理”。新任务默认追加到队列；提供明确的“清除已完成记录”操作，必要时在清除前确认。首个改进版本可以只把任务状态和选项保存在当前会话，之后再引入跨重启历史。至少应提供活动中、已完成、失败/取消筛选及任务数量汇总。

成熟下载器将暂停/恢复、移除、队列和任务选择等动作作为任务列表的操作。Motrix 项目说明可作为此类下载器工作流的实例参考。[Motrix 中文项目说明](https://github.com/agalwood/Motrix/blob/main/README.zh-CN.md)

代码依据：[任务表重建](../src/djhx_bilix/gui/app.py#L434)、[批次开始逻辑](../src/djhx_bilix/gui/app.py#L454)、[当前任务列表限制](gui-usage.md)。

#### 4.3 重试必须说明范围和使用哪套设置

当前“重试失败项”会一起选择失败与取消项，并以点击重试时的当前设置重新执行。若用户已经更改了画质、音轨、目录或覆盖选项，重试的行为就不再等同于原任务；按钮也不能让用户挑选某一项。

建议首先支持逐项重试。对批量操作提供清楚选项：“按原任务设置重试”和“按当前设置重试”；执行前展示会重试的项目数。取消和失败应保持不同状态，并支持分别筛选。任务列表应说明错误原因和下一步动作，例如重新登录、降低画质、检查目录权限或重试。

CLI 错误处理也应逐步提供稳定错误类别与下一步建议，同时继续屏蔽可能包含凭据或签名 URL 的第三方原始异常。命令行设计指南强调报错应简洁、准确，并帮助用户决定下一步。[Command Line Interface Guidelines](https://clig.dev/)

代码依据：[GUI 批量重试选择](../src/djhx_bilix/gui/app.py#L478)、[下载设置快照](../src/djhx_bilix/gui/app.py#L463)、[CLI 异常处理](../src/djhx_bilix/cli.py#L69)。

#### 4.4 预览计划应检查文件冲突和最终结果

dry-run/预览当前展示规划出的文件名和媒体选择，但未明确列出目标文件已存在、将被跳过或将被覆盖的数量。用户可能要等实际执行后才发现文件被跳过，或因为勾选覆盖而替换了同名输出。

建议预览里逐项标明“新下载 / 已存在会跳过 / 确认后覆盖 / 计划失败”，并在批次顶部统计数量。覆盖操作可在预览结果上确认具体目标文件；下载核心继续维持“新文件校验后再替换旧文件”的安全提交方式。完成后提供“打开文件”“打开所在目录”和“复制路径”，不要只依赖双击表格这一不明显的入口。

代码依据：[GUI 预览与计划显示](../src/djhx_bilix/gui/app.py#L604)、[同名文件跳过与覆盖提交](../src/djhx_bilix/service.py#L46)、[打开输出目录](../src/djhx_bilix/gui/app.py#L368)。

#### 4.5 简化下载页首屏，把高级选项渐进披露

下载页同时展示画质、编码、音轨、选集、严格匹配和覆盖选项，且音轨、编码、strict 等术语没有解释。对只想粘贴链接的用户，这让“怎么开始”变成“先理解一排选项”。

建议首屏默认只展示地址、保存位置、自动画质和主要下载动作；编码、音轨、严格匹配、覆盖放入“更多选项”。文案应描述结果而不是内部参数，例如：“开启后，所选画质不可用时停止；关闭后，自动选择较低的可用画质”。可在选择器里标明“自动：按当前账号可获取的最高画质”，并提示 AAC/FLAC/Dolby 的兼容性差异。

GNOME 设计原则建议减少同时出现的元素、使用渐进披露并降低完成常见任务所需的步骤。BiliX 使用 Qt 且面向 Windows/Linux，具体布局应结合目标平台验证，而不是直接照搬 GNOME 组件风格。[GNOME 设计原则](https://developer.gnome.org/hig/principles.html)

代码依据：[GUI 下载选项表单](../src/djhx_bilix/gui/app.py#L130)。

#### 4.6 展示当前生效配置及其来源

配置加载支持环境变量覆盖 TOML 文件；GUI 设置页虽然提示环境变量优先，但没有逐项标出当前生效值来源。用户编辑配置文件字段时，可能误以为保存后它就会成为实际下载目录或 FFmpeg 路径。

建议把配置值和有效值区分展示，并说明来源：程序默认、配置文件、环境变量或当前批次覆盖。被环境变量覆盖的字段可以显示为“当前由环境变量控制”，并提供相应变量名。当前 GUI 会把加载到的设置值放入编辑框；当这个值来自环境变量时，保存操作仍会写入配置文件，但环境变量会继续优先生效。界面应避免让用户误以为保存已经改变实际行为。下载目录和 FFmpeg 路径保存后，可显示校验结果或“待诊断”，避免路径无效后才在下载时发现。

代码依据：[配置优先级](../src/djhx_bilix/config.py#L30)、[GUI 设置读取/保存](../src/djhx_bilix/gui/app.py#L299)。

### P1：完善任务执行期间的可见性和控制

#### 4.7 进度同时表达单项、阶段和整批状态

GUI 的单一进度条主要代表当前媒体传输或媒体处理阶段；队列是串行的，因此用户无法由此判断整批还有多少项。GUI 也不显示速度和 ETA，而 CLI 的 Rich 进度栏已经有速度/剩余时间字段。

建议在任务行显示当前项的速度与阶段，在批次总览显示已完成/总数和失败数。已知总大小时显示 ETA；未知时不要猜测，改为显示“读取信息”“校验视频”“合并音视频”等阶段。明确标示串行队列中当前任务与等待任务。下载失败时保留任务行上的详细原因和重试入口。

GNOME 进度模式指导可以作为指示器和状态文本的参考；该指南面向 GNOME 应用，BiliX 还应结合 Qt 在 Windows/Linux 桌面的呈现进行验证。[GNOME 进度条指南](https://developer.gnome.org/hig/patterns/feedback/progress-bars.html)

代码依据：[GUI 进度和阶段事件](../src/djhx_bilix/gui/app.py#L612)、[CLI 进度栏](../src/djhx_bilix/presentation.py#L71)。

#### 4.8 区分取消当前任务、停止队列和关闭程序

当前取消按钮名为“取消当前操作”，实际下载操作会结束当前批次，未完成行随后被标记取消；关闭运行中的主窗口会自动请求取消并等待 worker 退出。用户不容易预知“取消”会影响当前一项还是整批，也没有转入后台继续运行的选择。

建议将任务级取消与批次级停止分开：任务行提供取消该项，批次栏提供停止后续任务；关闭时说明正在运行的任务是否会停止及临时文件如何处理。若未来加入托盘或后台运行，应单独设计而非假定所有用户都想要常驻后台。

GNOME 对话框指南建议避免不必要的打断，但对无法撤销、后果不明显的操作，应清楚说明将发生什么；常见状态变化适合在上下文中反馈。[GNOME 对话框指南](https://developer.gnome.org/hig/patterns/feedback/dialogs.html) [GNOME Toast 指南](https://developer.gnome.org/hig/patterns/feedback/toasts.html)

代码依据：[取消操作](../src/djhx_bilix/gui/app.py#L573)、[关闭时请求取消](../src/djhx_bilix/gui/app.py#L789)、[下载取消与临时目录清理](../src/djhx_bilix/service.py#L152)。

#### 4.9 GUI 登录状态要减少“未知”状态

启动后账号页显示“点击查询状态”，用户无法知道本地是否有凭据，也不知道凭据是否过期。考虑到匿名下载也是有效路径，建议启动时先显示本地凭据状态；网络账号状态继续由明确的“检查登录状态”动作触发，或在用户首次选择需登录能力时提示登录。状态文字要区分未登录、凭据存在但未核验、登录有效、登录失效和网络检查失败。

代码依据：[账号页面初始状态](../src/djhx_bilix/gui/app.py#L238)、[账号状态实现](../src/djhx_bilix/auth.py#L149)。

#### 4.10 GUI 需支持键盘、高 DPI、小窗口与偏好记忆

GUI 使用常规 Qt Widgets 是合适的起点，但现有文档明确记录了完整快捷键体系、DPI/小屏和部分 Linux 桌面行为仍有验证缺口。建议加入合理的快捷键和焦点顺序、窗口大小与常用选项记忆，并测试缩放、路径截断、中文输入法、键盘操作和屏幕阅读辅助信息。常用设置记忆应与下载业务配置分开存放。

Windows 键盘交互指南强调可预测的焦点顺序、键盘导航和快捷键；GNOME HIG 提供标准快捷键及动态尺寸适配建议，可作为交叉检查清单。[Windows 键盘交互指南](https://learn.microsoft.com/en-us/windows/apps/develop/input/keyboard-interactions) [GNOME 标准快捷键](https://developer.gnome.org/hig/reference/keyboard.html) [GNOME 适配与缩放](https://developer.gnome.org/hig/guidelines/adaptive.html)

代码/验收依据：[窗口默认与最小尺寸](../src/djhx_bilix/gui/app.py#L95)、[1.6.0 未完成验证范围](validation-1.6.0.md#L52)。

### P1：CLI 对人类用户与自动化脚本都更友好

#### 4.11 统一帮助语言，增强示例和错误恢复路径

本次查看 CLI 实际帮助发现，命令描述主要是中文，但 Usage、Options、Show this message and exit 等框架文字仍为英文。主帮助提供命令列表，却没有按常见任务给出可复制的登录、查看权限、预览下载、批量下载示例。

建议为根命令和高频子命令补充从“第一次使用”到“发生错误”的短示例；对于画质降级、音轨不可用、登录过期等错误，指出推荐命令或参数。保留现有拼写建议和 shell 补全，这是有效的 CLI 可发现性能力。

Command Line Interface Guidelines 建议 CLI 提供完整帮助、示例和对错误的下一步建议；GNU Coding Standards 规定显式 --help 应将帮助写到标准输出并以成功状态退出。[Command Line Interface Guidelines](https://clig.dev/) [GNU Coding Standards：命令行接口](https://www.gnu.org/prep/standards/standards.html)

代码依据：[Typer 根命令配置](../src/djhx_bilix/cli.py#L36)、[download 参数帮助](../src/djhx_bilix/cli.py#L169)、[拼写与补全说明](completion.md)。

#### 4.12 提供一致的配置修改入口

CLI 的 config 目前只读出配置位置、下载目录和 FFmpeg。CLI-only 用户若要修改默认值，需要手动编辑 TOML、设置环境变量或另行使用 GUI。

建议增加配置列出、查看、设置、重置和校验操作；显示每个值的来源及环境变量覆盖情况。写入应保留当前原子替换语义，并在设置成功后告诉用户新值和生效范围。GUI 与 CLI 调用同一份配置服务。

代码依据：[CLI config 命令](../src/djhx_bilix/cli.py#L322)、[配置保存](../src/djhx_bilix/config.py#L56)。

#### 4.13 把人类输出与机器输出分离

当前 info 与账号状态支持 JSON；下载命令输出人类可读的进度与最终摘要，但没有下载过程事件流或结构化错误码。脚本若要识别哪些任务完成、跳过或失败，只能解析文本。

建议为 download 增加可选 JSON Lines 模式，输出稳定的任务 ID、状态、阶段、字节、速率、ETA、输出路径和错误码；机器协议写到 stdout，诊断提示写到 stderr。任务事件不得包含 Cookie、二维码数据或临时签名媒体地址。保留现有默认终端体验和退出码。

yt-dlp 的官方命令行文档展示了成熟媒体 CLI 对进度模板、重试、继续下载和批处理输入的显式控制，可用于设计自动化接口，但不必复制其所有参数。[yt-dlp 命令行与进度选项](https://github.com/yt-dlp/yt-dlp/blob/master/README.md) BiliX 路线图已有结构化事件和脱敏验收方向，可直接沿用。[BiliX 路线图](roadmap.md)

代码依据：[下载输出与汇总](../src/djhx_bilix/cli.py#L221)、[现有 JSON 输出](../src/djhx_bilix/cli.py#L133)。

#### 4.14 支持通过标准输入组合批处理命令

CLI 已支持 URL 文件，但不支持从 stdin 读取列表。建议允许文件参数使用 “-” 代表 stdin，使其他命令、脚本和管道能动态生成地址列表；错误信息应包括输入行号，并明确如何跳过注释、空行和重复项。

Command Line Interface Guidelines 建议文件输入/输出接口支持 “-” 约定，以便与 Unix 管道组合。[Command Line Interface Guidelines：文件与标准流](https://clig.dev/)

代码依据：[URL 文件读取](../src/djhx_bilix/urls.py#L76)、[CLI 文件参数](../src/djhx_bilix/cli.py#L197)。

#### 4.15 整理兼容别名，让帮助优先呈现推荐用法

下载帮助同时显示 --file、--origin 和 -o；download --info 是兼容旧版的查看入口，另有隐藏的旧 video 命令。兼容旧用户是合理的，但主帮助更应清楚地回答“现在推荐怎么写”。

建议在帮助中标注旧参数和兼容期限，将迁移说明链接到 releases 文档；新手快速示例只展示 info、download 和 auth 等规范命令。若移除兼容入口，应有明确版本政策，不宜悄悄改变既有脚本行为。

代码依据：[下载命令参数与兼容选项](../src/djhx_bilix/cli.py#L197)、[隐藏 legacy 命令](../src/djhx_bilix/cli.py#L345)。

### P2：作为下载器持续演进的能力

#### 4.16 设计暂停、恢复和崩溃后续传

暂停/恢复是下载器的典型期望，但 BiliX 当前不把失败临时目录视为续传数据，也没有验证分片与当前媒体身份的恢复契约。建议先设计恢复模型：保存稳定的源 URL、选集、选项、目标路径和必要的本地分片元数据；恢复时重新解析短期媒体地址并验证远端身份、Range 响应和数据长度。坏分片不能提交为最终文件。

yt-dlp 提供继续下载、分段重试等终端行为；Motrix 的说明体现了桌面任务暂停/恢复和会话管理。它们适合作为用户预期和交互模式参考，实际机制仍应符合 BiliX 的签名 URL、权限和事务安全约束。[yt-dlp 下载选项](https://github.com/yt-dlp/yt-dlp/blob/master/README.md) [Motrix 中文项目说明](https://github.com/agalwood/Motrix/blob/main/README.zh-CN.md) BiliX 已在路线图中记录续传的 Range、身份与长度校验条件。[BiliX 下载恢复计划](roadmap.md)

#### 4.17 在明确预算下增加并发和限速

当前视频任务串行执行，每个任务内部音视频流并行。后续可考虑可配置的同时任务数与下载速度限制，但应将“视频任务并发”和“音视频连接数”作为不同预算管理；先保证任务取消隔离、连接数量有界，再向用户开放参数。

Motrix 项目列出多任务并发和速度限制作为下载管理能力；yt-dlp 同样提供并发分片与限速选项，可作为 CLI 参数和说明方式的参考。[Motrix 功能说明](https://github.com/agalwood/Motrix/blob/main/README.zh-CN.md) [yt-dlp 下载选项](https://github.com/yt-dlp/yt-dlp/blob/master/README.md) BiliX 路线图也提出了连接预算和并发边界。[BiliX 并发规划](roadmap.md)

#### 4.18 在任务持久化前先定义脱敏与可恢复边界

如果引入跨重启队列和历史，持久化内容应限于恢复所需的稳定信息，不应保存 Cookie、二维码 key 或短期 CDN 签名地址。应用退出时要把正在运行的项目标记为中断，重启后重新解析权限与媒体信息。

代码架构已有相同方向：路线图要求任务记录只保留规范化源地址、选集、选项和目标信息，不保存凭据或临时签名地址。[BiliX 共用任务与隐私边界](roadmap.md)

## 5. 建议的信息架构

### GUI 下载工作区

推荐围绕“新增任务 + 任务队列”组织下载页：

1. **新增下载**：粘贴一条或多条地址、导入列表；明显区分“加入队列”和“立即开始”。
2. **基础设置**：保存位置、自动画质；新用户无需先理解编码和音轨。
3. **高级设置**：编码、音轨、严格匹配、覆盖、选集规则；显示清晰解释和默认行为。
4. **队列区**：待处理、活动、已完成、失败/取消；可追加任务、筛选、重试、取消和移除。
5. **任务详情**：目标路径、实际选择的流、进度阶段、错误原因、输出文件操作。

批次执行前应能确认实际会下载哪些 P、采用什么清晰度/编码/音轨、是否会跳过或覆盖现有文件。队列和历史可以分阶段实现；暂停与续传则应等待底层恢复方案通过验证。

### CLI 的推荐交互

保持“命令适合脚本、输出适合终端”的定位：

1. 帮助包含常见任务示例，并将参数按“基本下载 / 选集和媒体 / 高级行为”组织。
2. info 用于理解内容和账号可用媒体，dry-run 用于确认计划，download 执行实际下载；错误提示给出能直接运行的下一条命令。
3. 默认输出继续面向人类；显式 JSON/JSONL 模式面向脚本，数据字段和错误码有版本契约。
4. 保持补全、拼写纠错、批量文件和传统退出码，不让新增交互破坏现有自动化。

## 6. CLI 与 GUI 的一致性要求

两种前端无需长得一样，但结果和语义应一致：

| 行为 | 一致性要求 |
| --- | --- |
| 默认画质和降级 | 两端对“自动”“指定最高限制”和降级规则的解释一致 |
| 编码和音轨 | 可用项、失败原因和实际选中项一致 |
| 多 P 与 URL 中的 p 参数 | 未填写选集时的默认行为一致；GUI 应把实际选集可视化 |
| 覆盖与文件冲突 | 均清楚展示跳过/覆盖行为；内核继续保护旧文件 |
| 错误分类 | 机器错误码共用，CLI 与 GUI 分别呈现合适的下一步操作 |
| 进度事件 | 共用任务 ID、状态、阶段和字节数据；Rich 和 Qt 各自适配显示 |
| 设置 | 两端显示相同的有效路径与来源优先级 |

建议先在纯 Python 层定义任务 ID、任务状态、阶段事件、错误码和脱敏结果，再由 Rich CLI 和 Qt UI 分别展示。CLI 不应解析终端渲染文字，GUI 也不应直接呈现内部 JSON 或第三方异常。

## 7. 建议的推进与验收

### 第一阶段：现有功能的体验修正

- GUI 信息面板替换原始 JSON 展示，并实现多 P 的可视选择。
- 新批次不再静默清空已有任务；加入逐项重试和明确的重试设置来源。
- dry-run 展示任务数量、输出冲突、跳过与覆盖结果。
- 简化下载页首屏，显示配置来源、当前任务与批次状态。
- CLI 帮助统一主要界面语言，补齐高频用法示例和可执行的错误恢复建议。

验收重点：用户在启动下载前能说清“会下载哪些项、保存到哪里、画质如何选择”；批次失败后能仅重试需要的项目，且知道使用哪套选项。

### 第二阶段：任务控制和可观测性

- 支持运行中追加任务、单项取消、单项重试和队列筛选。
- 增加每任务速度/阶段/可用 ETA 与批次汇总。
- 提供下载 JSONL 事件与稳定错误码，保护凭据和签名地址不进入输出。
- CLI 增加可校验的 config 修改能力与 stdin 批量输入。
- 增加诊断信息复制/导出，并对可导出字段进行脱敏审核。

验收重点：同一个任务在 CLI/GUI 中结果一致；自动化不需解析 Rich 文本；GUI 在大量任务时仍能明确控制单项和批次。

### 第三阶段：恢复、持久化和性能控制

- 定义持久任务记录格式、迁移和中断状态。
- 设计并验证 Range 续传、短期媒体地址重新解析和分片校验。
- 实现任务并发预算和限速，再提供用户设置。
- 做 Windows/Linux 小窗口、高 DPI、键盘与输入法的实际桌面验收。

验收重点：重启后可识别中断任务；恢复不会把错误媒体提交为最终文件；取消一项不会误伤其他任务；连接与磁盘使用量有界。

| 4.14 stdin 批量输入 | 成立，成本低 | `urls.load_urls` 只需接受 `-` 分支；可顺带补行号、去重与注释语义 |

| 4.16 暂停/恢复/续传 | 定位正确 | 风险最高；需先定义恢复契约，并确定“失败保留临时目录、取消删除临时目录”中哪一类可续传 |
| 4.17 并发与限速 | 定位正确 | 需区分视频任务并发与单任务内音视频双连接预算 |
| 4.18 持久化脱敏边界 | 定位正确 | 与 roadmap 及 `validation-1.6.0.md` 的隐私要求一致 |

### 10.3 需要修正的表述

1. **4.4“只依赖双击表格”不准确。** 界面已有“打开输出目录”按钮；真正缺少的是“打开文件”和“复制路径”。
2. **4.11 的 GNU `--help` 语义当前已满足。** 实测 `python -m djhx_bilix --help` 退出码 0、stderr 为空、帮助写 stdout；真缺口只是框架文案语言与可复制示例。
3. **4.2 的影响范围应写得更重。** “重试失败项”同样会重建任务表并抹掉已完成记录，不只是“开始新批次”时发生。
4. **4.15 未指出 `-o` 语义冲突。** `download`/`info` 的 `-o` 当前等价于 `--file`（实测帮助为 `--file,--origin  -o`），与“输出”惯例冲突。既有脚本依赖该别名，不能重定义，只能在帮助中降低其推荐度并说明迁移方向。

### 10.4 建议补入的内容

1. **成本分级。** 文案与布局改动、取消模型改造、续传属于不同量级，不应放在同一优先级层级，否则容易误导排期。
2. **共用事件契约的现状。** `operations.StageEvent` 与 `worker` 的事件字典已是雏形；缺的是版本化的纯 Python 事件对象（任务 ID、状态、阶段、字节、错误码、脱敏结果）。补齐它可一次性解锁 4.7、4.13、4.18，建议列为第一优先。
3. **平台取向校准。** 本项目 GUI 当前只支持 Windows 与 Ubuntu/Debian（macOS 未纳入），引用应以 Windows 键盘/DPI 规范为主、GNOME HIG 为辅。
4. **可测性。** `tests/gui` 已有 pytest-qt + offscreen 交互回归，本评审多数建议可写成离线测试，这是其可执行性的有力条件。

### 10.6 必须保留的边界

- 保持 `service.commit_file` 的“校验后再原子提交、普通失败保留临时目录”语义，任何界面改动不得绕过。
- 重试与恢复都不得把未通过 `media.check_stream` 的分片提交为最终文件。
- 任务事件与机器输出不得包含 Cookie、二维码数据或签名 CDN URL；`public_dict` 与 `worker` 的异常兜底是正确样例，新协议必须沿用。
- GUI 偏好（窗口/选项记忆）应与 `config.toml` 分离，避免污染 CLI 的有效配置语义。
