# 持续测试与版本验收

此规范从首个 GUI 版本 1.6.0 开始维护，适用于后续 CLI、GUI 和共享内核。通用步骤留在本文与平台流程；每个版本的实际结果单独保存为 `docs/validation-<版本>.md`，使用[验收模板](validation-template.md)。历史通过记录只能作为比较基线。

## 日常可重复入口

CLI 环境：

```shell
uv sync --locked
uv run --locked python scripts/validate.py --profile cli
```

GUI 环境：

```shell
uv sync --locked --extra gui --group gui-test
uv run --locked --extra gui --group gui-test python scripts/validate.py --profile gui
```

验证入口先比对源码版本与已安装 `djhx-bilix` 发行元数据；不一致直接失败并保留报告。不要使用会优先加载旧 `src/*.egg-info` 的 PYTHONPATH 覆盖来绕过检查。应在隔离环境重新安装当前 checkout/最终 wheel，并确认版本身份。

GUI profile 运行全部共享内核、CLI、GUI 测试，CLI profile 明确排除 `tests/gui`。GUI profile 缺少 PySide6 或 pytest-qt 时直接失败，防止整个 GUI 测试目录被 `importorskip` 跳过后误报完成。脚本检查文档的相对文件链接、Ruff、pytest、CLI 帮助/版本/诊断/纠错/四种补全脚本，以及 GUI 离线启动。链接检查只验证文件存在；标题锚点、远程链接和页面交互仍需人工检查。

每次结果在 `build/validation/<版本>/<profile>-<UTC时间>-<随机数>/`，包括 `result.json`、逐步骤日志和 `pytest.xml`。记录 Python/依赖版本、提交、工作树状态、失败和每项 skip 原因；失败返回非零退出码，重跑不会覆盖旧证据。账号、下载和 pytest 临时目录独立；脚本不读取日常账号，不启动 VM，不执行在线登录、上传或部署。

需要完整 FFmpeg 才能生成合成媒体，Linux 还需 ffprobe。用 `BILIX_TEST_FFMPEG` 指定测试编码器；被测扫描/合并仍由项目实际 FFmpeg 完成。普通开发可缺少部分能力，但必须复核 skip。Windows 全能力发行验收使用 `--strict-skips`；Linux 的 Windows 专用 skip 逐项记录，不能为了清零而屏蔽其他测试。

对已经集合好的最终包做只读复核：

```shell
uv run --locked --extra gui --group gui-test python scripts/validate.py --profile gui --strict-skips --release-dir dist/release-1.6.0
```

把目录替换为候选版本。此检查核对八个版本化产物、大小、SHA256、校验清单、归档安全路径及关键元数据/材料，不改写发行目录。使用与产物版本匹配的 checkout；原始源码逐文件对应和冻结程序编译来源还需单独留证。`assemble_release.py` 用于候选集合，会写文件，不能拿它复核已经公开且不可变的发行包。

## 测试层级与执行频率

| 层级 | 检查与证据 | 何时执行 |
| --- | --- | --- |
| T0 静态/文档 | Ruff、相对链接、帮助与说明一致、页面键盘和窄屏检查 | 每次修改；页面交互仅页面变化时 |
| T1 共享内核与 CLI | 纯逻辑、本地 HTTP 故障、合成媒体、退出码、安全与补全回归 | 代码修改；每次候选全量 |
| T2 GUI 离线交互 | pytest-qt、worker 生命周期、窗口关闭、取消、重试、配置共享、脱敏 | GUI/内核修改；每次候选全量 |
| T3 Python 分发 | 隔离环境安装最终 wheel，CLI 无 Qt、GUI extra、入口、最低 Python | 每次候选；依赖变化扩大解释器矩阵 |
| T4 原生包 | 各目标平台构建/运行、校验、干净安装、重装、升级、卸载、数据保留 | 每次原生产物变更 |
| T5 真实桌面 | 字体、键盘、IME、DPI、文件选择器、二维码、窗口生命周期 | 每次 GUI 候选；布局/Qt 变化全面复验 |
| T6 在线业务 | 受控账号扫码、权限、实际下载和 CLI/GUI 结果对照 | 发布候选；登录/API/媒体行为变化必须安排 |
| T7 发布核验 | 同源码产物、许可/源码、凭据扫描、公开文件回下载哈希 | 每次发布前及发布后 |

开发时按影响选择检查；发行时共享内核与两个前端一起回归。Qt/原生依赖变化重新执行全部支持平台的 T4/T5；文档或许可进入候选包后重新打包并按新哈希验收。公开发行包、标签和同版本 PyPI 文件保持不可变，本次维护不会改写 v1.6.0 已发布产物。

用例 ID 保持稳定，新功能增加 ID；删除用例须解释被替代的风险。自动覆盖以当前 `tests/` 为准，表中的人工场景须在版本记录中填写状态。

| ID | 场景与通过标准 | 执行方式 |
| --- | --- | --- |

| CORE-02 | 清晰度/编码/音轨降级、strict、试看/DRM、会员失效 | 合成响应；授权账号对照 |

| CORE-05 | 传输/校验/合并/提交边界取消；完成文件有效，无遗留子进程 | 自动阶段故障注入；原生包桌面复验 |
| CLI-01 | 两个命令名与模块入口、兼容入口、JSON 无秘密、退出码 0/1/2/130 | pytest；安装最终 wheel/exe |

| GUI-02 | 扫码生成/扫描/确认/过期/取消、关闭弹窗、账号查询取消 | 模拟事件；授权账号实际流程 |
| GUI-03 | 运行中关闭窗口、取消两路与 FFmpeg、稍后可重新操作 | pytest-qt；桌面阶段抽查 |

| REL-01 | 同版本完整产物、许可证/源码、无凭据/本地状态、公开哈希一致 | 包检查、扫描、回下载 |

磁盘不足、无目录权限、代理/离线与慢请求要分别安排，不能用一个“网络错误”覆盖所有场景。新并发/历史/更新功能必须新增任务隔离、迁移/恢复、真实性校验等用例。

1.7 的新增产品用例 TASK/INFO/SESSION/PLAN/CONFIG-17/ACCOUNT-17/CANCEL-17/CLI-17/UX-17 及 B-* 的准确 ID、场景和通过标准集中维护在[开发指南验收矩阵](cli-gui-ux-review.md#9-验收矩阵与发布门槛)。A 为必做范围，B 只有实际纳入功能冻结后才成为该候选的验收要求。`tests/prototypes/test_ux_17.py` 验证隔离设计实验，不证明正式 1.7 能力实现；对应覆盖与未验证范围见[设计验证记录](validation-1.7-design.md)。

1.7.3 的 GUI 布局与交互新增用例 GUI173-01 至 GUI173-13 见[版本指南](gui-update-guide-1.7.3.md#9-定向验收)，复用现有行为测试，按实际界面变化做定向原生检查。共享下载内核/安装器输入未变时不重复扩大权限或安装故障矩阵；如这些输入发生变化，按影响补测。本版不承担 B 功能版验收，开发指南也不代表候选已经通过。

产品实现的纯任务模型、来源/尝试隔离、身份校验、重试、单一终态、取消和只读预览回归在 `tests/test_tasks.py`；正式窗口的跨批次历史、选集、参数快照、配置覆盖、离线账号和关闭流程在 `tests/gui/test_tasks_gui.py`。`scripts/validate_tasks_gui.py` 对生产窗口运行 100/1000 项合成任务及 800×600 布局测量；这些离线检查不能替代原生桌面和真实账号验收。该版本的实际结果集中记录在[1.7.0 验收记录](validation-1.7.0.md)。

## 环境与平台矩阵

- Python：3.11 的隔离 CLI/GUI wheel 为最低版本检查；锁定的构建解释器执行全量。3.12/3.13 的安装/入口检查及必要回归单独填写，没跑不能沿用旧记录。
- Windows：CLI 在无 Qt 的独立环境构建；GUI onefile/standalone/安装器分别验证。PowerShell 5.1 与 7 分别记录。当前 GUI 原生目标为 Windows 10 22H2 x64，加入 Windows 11 后增加独立一列。
- Linux：Ubuntu 22.04 构建，同一 deb 在 Ubuntu 22.04/24.04、Debian 12/13 amd64 干净环境安装。Xvfb/X11、可见桌面、无头 Weston、GNOME/KDE Wayland 分开填写。
- macOS/ARM 等新目标在具备原生构建和完整验收后加入。Python 元数据允许安装不等于此次验证了所有系统。

[Windows 流程](gui-win10-validation.md)与[Linux 流程](gui-vm-validation.md)负责平台操作。Linux 脚本从指定目录的 manifest 选定 deb，允许其他版本文件并存；每轮日志独立保存。Windows 脚本兼容分平台或完整清单，同样按 manifest 和独立结果目录执行。平台脚本通过不代表 T5/T6 通过。

## 升级与数据保留

首版没有旧稳定 GUI 包，PKG-02 的跨版本升级为“不适用：首版”，不能记作通过。从下个 GUI 版本开始保留 1.6.0 作为真实升级基线，使用同一稳定安装身份；Preview 的单独 AppId 不能代替稳定升级。

在隔离用户目录先用旧版本创建非默认配置、测试凭据占位文件和下载标记，记录内容哈希；结束任务并关闭应用后升级，验证配置可读、文件完整、版本正确、启动正常及卸载保留数据。占位文件不能证明真实凭据仍有效，在线账号检查另行记录。Windows 通过 `-PriorSetup` 加入旧安装器；Linux 先 `apt install` 旧 deb，再新 deb，并核对 `dpkg-query` 的版本与标记。低版本行为按渠道规定验收：后续 Windows 新安装器应在改文件前拒绝覆盖较新的同渠道安装，但不能保证已发布且无检测逻辑的 1.6.0 旧安装器也会拒绝，须实测该方向并记录限制；APT 显式降级遵守包管理器策略，不宣称 deb 自带降级阻止。新检测逻辑、真实旧包行为和写入失败恢复分别留证，详细情形见[指南升级边界](cli-gui-ux-review.md#92-升级降级准确边界)。

## 结果判定与发布门槛

仅使用“通过、失败、未验证、不适用”。skip 记录原因及对应环境；未经执行的桌面、在线业务和平台不能标成通过。每项证据绑定版本、提交/工作树、产物哈希、系统和执行时间。

代码/媒体/文件事务/凭据保护失败、候选安装或启动失败、同源码/哈希不一致、许可材料缺失均阻止发行。缺少环境、测试账号或设备时记录未验证、责任人和补测范围；维护者必须明确接受范围限制并同步发行说明，不能让脚本的绿色状态自动代替完整发布决策。首版已公开的验证缺口在[1.6.0 记录](validation-1.6.0.md)保留，下一版优先补测。

发布后仅能确认公开下载和安装行为；发现需要修改代码或发行材料的问题使用新的版本号。实际授权发布步骤仍按[维护者流程](releasing.md)执行。
